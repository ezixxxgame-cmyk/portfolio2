# AGENTS.md — разработка лендингов

Правила для AI-агента при создании и доработке одностраничных сайтов.
Приоритеты: точное выполнение задачи, качественный интерфейс, адаптивность, простой код и экономный расход токенов.

## Репозиторий проекта Complimento

* GitHub: https://github.com/ezixxxgame-cmyk/complimento
* Адрес `origin`: https://github.com/ezixxxgame-cmyk/complimento.git
* Ветка для коммитов и публикации: `main`.
* Для этого проекта используй указанный репозиторий, в том числе в новых чатах. Коммиты и push выполняй только по явному запросу пользователя, согласно разделу 4.

## 1\. Область работы

* Работай только внутри текущего репозитория, кроме узкого исключения для Obsidian Vault из раздела 12.
* Перед изменениями кратко изучи структуру, стек и существующие соглашения проекта.
* Не читай и не изменяй другие проекты, пользовательские файлы и системные настройки. Единственное исключение — работа с Markdown-заметками внутри Obsidian Vault по правилам раздела 12.
* Не создавай журналы, handoff-файлы и лишнюю документацию без запроса.

## 2\. Тип и границы задачи

Сначала определи, к какому типу относится запрос:

* новый лендинг;
* дизайн или редизайн;
* техническое исправление;
* добавление функциональности;
* контент;
* рефакторинг;
* SEO.

Работай только в рамках текущего типа задачи.

* Не меняй несвязанные секции, стили, тексты, конфигурацию и функциональность «заодно».
* Не переходи к дизайну, SEO, рефакторингу или другим видам работ без запроса.
* Не перезаписывай незнакомые пользовательские изменения.
* Предпочитай минимально достаточный diff.
* Задавай вопрос только тогда, когда без ответа велик риск сделать неправильный результат.

## 3\. Skills

Всегда используй следующие Skills при выполнении любой задачи, если они доступны:

* `ponytail` — для выбора самого простого достаточного решения без лишних абстракций, зависимостей и переусложнения кода.
* `caveman ultra` — для кратких, прямых ответов без длинных отчётов и лишнего расхода токенов.

Остальные специализированные Skills используй только тогда, когда они действительно относятся к текущей задаче.

* `ui-ux-pro-max` используй только при создании нового дизайна, редизайне или явном запросе улучшить внешний вид.
* Не меняй дизайн при технических исправлениях, если пользователь этого не просил.
* SEO Skills используй только по явному запросу пользователя.
* Используй скилл impeccable при создании дизайна и редизайне сайта. Он важен чтобы не было ии-слопа
* Если пользователь указал конкретный Skill, используй его только в рамках текущей задачи вместе с обязательными `ponytail` и `caveman`.
* Если обязательный Skill недоступен, не останавливай работу: следуй его принципам на основе этого `AGENTS.md`.

## 4\. Опасные операции

Без прямого запроса пользователя запрещено:

* удалять файлы, секции или существующую функциональность;
* устанавливать, удалять или обновлять зависимости;
* менять `package.json`, lock-файлы, `.env`, сборку и деплой;
* выполнять `commit`, `push`, `merge`, менять ветки или создавать pull request;
* запускать deploy;
* проводить массовый рефакторинг или форматирование всего проекта.

### GitHub и ветки

* Не создавай ветки на GitHub, pull request или fork, если пользователь прямо не попросил об этом.
* Если пользователь явно попросил опубликовать изменения, работай только с веткой `main`: коммиты и push выполняй в `main`.

Если доступен и уже авторизован GitHub-плагин, используй его для действий с GitHub. Не запрашивай GitHub CLI, токен, логин или другие учётные данные: плагин использует собственную авторизацию. Ограничения на commit, push, ветки и pull request из этого раздела сохраняются.

Если новая зависимость или изменение конфигурации действительно необходимы, сначала кратко объясни причину и запроси подтверждение.

## 5\. Реализация

* Сначала используй существующие компоненты, стили, утилиты и зависимости.
* Выбирай самое простое решение, которое полностью решает задачу.
* Не создавай абстракции, хуки и компоненты «на будущее».
* Не дроби простую секцию на множество файлов без пользы.
* Повторяющийся или самостоятельный UI выноси в компонент; одноразовую локальную разметку оставляй рядом с секцией.
* Не добавляй backend, базу данных, авторизацию, CMS или API, если задача этого не требует.
* Не применяй архитектуру SaaS-приложения к обычному лендингу.

## 6\. Дизайн

Применяй этот раздел только к задачам, связанным с созданием или изменением интерфейса.

* Следуй бренду, референсам и пожеланиям пользователя.
* Если стиль не задан, выбери одно ясное визуальное направление и придерживайся его на всей странице.
* Строй понятную иерархию: смысл, преимущества, доказательства, CTA.
* Используй согласованную систему отступов, размеров, радиусов, теней и типографики.
* Не перегружай страницу карточками, градиентами, свечением, blur и декоративными эффектами.
* Избегай шаблонного AI-дизайна: случайных цветов, одинаковых карточек и бессмысленного декора.
* Основной CTA должен быть заметным и понятным.
* Сохраняй хороший контраст и читаемость.
* Не используй эмодзи вместо интерфейсных иконок без запроса.

## 7\. Адаптивность

* Каждый изменённый UI-блок должен корректно работать на мобильных, планшетах и десктопах.
* Не допускай горизонтального скролла, обрезанного текста и выхода элементов за контейнер.
* Не фиксируй высоту текстовых блоков без необходимости.
* Учитывай длинные заголовки, переносы строк и реальные тексты.
* Кнопки и интерактивные области должны быть удобны для нажатия на телефоне.

## 8\. Изображения и анимации

* В первую очередь используй материалы пользователя.
* Не заменяй реальные изображения случайными заглушками без необходимости.
* Сохраняй пропорции изображений и выбирай подходящий `object-fit`.
* Добавляй содержательный `alt` значимым изображениям.
* Не подключай тяжёлые видео, ассеты или библиотеки без запроса.
* Анимации должны помогать восприятию, а не отвлекать.
* Не анимируй каждый элемент и не добавляй библиотеку ради простой анимации.
* Учитывай `prefers-reduced-motion` для заметного движения.

## 9\. Качество кода

* Следуй существующему стилю проекта и структуре каталогов.
* Используй TypeScript строго, если проект уже на TypeScript.
* Не применяй `any` без необходимости.
* Не оставляй отладочные логи, временные заглушки, закомментированный код и неиспользуемые импорты.
* Не дублируй крупные фрагменты разметки или данных.
* Не добавляй комментарии, которые пересказывают очевидный код.
* Используй семантический HTML, логичный порядок заголовков и корректные элементы: кнопки для действий, ссылки для переходов.
* Не удаляй focus-state без равноценной замены.
* Избегай лишнего JavaScript и ненужных клиентских компонентов.

## 10\. Проверка

После изменений выполняй только применимые и уже доступные проверки:

* синтаксис изменённых файлов;
* существующий lint или typecheck;
* сборку при существенных изменениях;
* изменённые блоки в браузере, если среда позволяет;
* минимум мобильный и десктопный размеры;
* отсутствие новых ошибок в консоли.

Не устанавливай инструменты только ради проверки. Не утверждай, что проверка выполнена, если она не запускалась.

Если проверка падает из-за старой проблемы вне задачи, не исправляй её автоматически — кратко сообщи об этом.

После завершения основной работы спроси пользователя, запустить ли отдельного субагента для поиска критичных ошибок в сделанных изменениях. Запускай такого субагента только после явного согласия пользователя.

## 11\. Общение и экономия токенов

* Не описывай каждый шаг работы.
* Не повторяй запрос пользователя без необходимости.
* Не составляй длинный план для простой правки.
* Не выводи полный код файлов без запроса.
* Не используй декоративные статусы, повторяющиеся эмодзи и формальные отчёты без пользы.
* Пиши кратко, но честно сообщай об ошибках и невыполненных проверках.
* Не составляй спецификации, технические задания или отдельные документы с требованиями, если пользователь прямо не попросил их.
* В ходе работы периодически сообщай прогресс: выполнено примерно N%, осталось примерно M%. Оценка приблизительная; пересматривай её при появлении новой информации.
* В финальном ответе обязательно коротко указывай использованные Skills. Если Skills не использовались, пиши: «Skills: не использовались».

Обычный финальный ответ:

```text
Готово.

Изменено:
- ...

Проверено: ...

Skills: ...
```

Указывай файлы и действия пользователя только тогда, когда это действительно важно.

## 12\. Obsidian как долговременная память

Используй Obsidian Vault как дополнительный источник контекста и долговременную память:

`C:\mozg\Мозг для работы`

Это единственное исключение из запрета читать и изменять пользовательские файлы вне текущего репозитория. Исключение действует только внутри указанного Vault и не разрешает читать или изменять соседние папки, другие проекты, пользовательские файлы и системные настройки.

### Границы доступа

* Разрешено выборочно читать, создавать и обновлять только Markdown-заметки внутри указанного Vault, когда это необходимо для текущей задачи или сохранения действительно полезного долгосрочного контекста.
* Не читай Vault целиком: сначала определи проект и тему, затем ищи только релевантные заметки.
* Не изменяй папку `.obsidian`, плагины, настройки, темы и другие служебные файлы без прямого запроса пользователя.
* Не удаляй заметки, не проводи массовое переименование или реорганизацию Vault без прямого запроса.
* Не копируй в Vault секреты, токены, пароли, содержимое `.env` и другие чувствительные данные.
* Правила этого раздела не отменяют запрет на лишнюю документацию: заметка допустима только как полезная долговременная память, а не как журнал работы, handoff или формальный отчёт.

### Перед значимой задачей

Проверь, есть ли в Vault релевантная информация о текущем проекте, прошлых решениях, ограничениях, известных проблемах, связанных людях и рабочих предпочтениях пользователя. Используй найденное как дополнительный контекст.

При конфликте источников соблюдай приоритет:

1. текущий запрос пользователя;
2. фактическое состояние кода и конфигурации текущего репозитория;
3. актуальная документация проекта;
4. заметки Obsidian.

Если заметка устарела, не следуй ей вслепую. При необходимости аккуратно обнови её, отделив текущее состояние от истории. Предположения отмечай как гипотезы, а неизвестность — как открытые вопросы.

### Структура Vault

Используй существующие папки по назначению:

* `00 Главная` — навигация и обзор ключевых областей; изменяй только при реальной пользе для навигации.
* `01 Я и мой контекст` — устойчивые предпочтения, цели и рабочий контекст пользователя.
* `02 Разработка сайтов` — повторно используемые знания о веб-разработке, подходах и технологиях.
* `03 Проекты` — состояние конкретных проектов, решения, ограничения, проблемы, следующие шаги и открытые вопросы.
* `04 Люди` — важный рабочий контекст, связи с проектами и договорённости; не сохраняй лишние персональные данные.
* `05 Решения и уроки` — значимые решения, причины, альтернативы, последствия и неочевидные уроки.
* `06 Вопросы и идеи` — гипотезы, идеи и открытые вопросы с понятным статусом.
* `07 Контекст для ИИ` — устойчивые инструкции и предпочтения, полезные будущим AI-агентам.
* `08 Источники` — ссылки и краткие выводы из внешних материалов с указанием их отношения к проекту.
* `09 Входящие` — временное место только когда подходящий раздел пока неясен; не превращай его в постоянное хранилище.
* `_Шаблоны` — существующие шаблоны заметок; используй подходящий шаблон, но не меняй шаблоны глобально без необходимости.

Перед созданием новой заметки проверь, нет ли уже подходящей. Предпочитай обновить одну актуальную заметку, а не создавать дубли. Добавляй `[[внутренние ссылки]]` только когда связь действительно полезна.

### Что сохранять после значимой работы

Без отдельной команды можно сохранить только информацию, которая поможет в будущей работе:

* важное решение и причины его выбора;
* новое ограничение, зависимость или существенную особенность проекта;
* сложную причину ошибки, важный edge case или полезный урок;
* существенное изменение состояния проекта;
* важный следующий шаг или открытый вопрос;
* явно выраженное устойчивое рабочее предпочтение пользователя.

Не сохраняй команды терминала, перечень изменённых файлов, обычные результаты сборки, мелкие правки, временный debugging-шум, быстро исправленные ошибки без полезного урока, очевидные факты из кода, повторы, полный разговор или внутренний chain of thought.

Перед записью проверь: поможет ли эта информация через неделю или месяц быстрее понять ситуацию, избежать повторной ошибки или принять лучшее решение? Если нет — не создавай и не обновляй заметку.

## 13\. Когда остановиться

Задай один конкретный вопрос, если:

* требования противоречат друг другу;
* требуется удаление или замена важной функциональности без явного запроса;
* без новой зависимости задачу невозможно разумно выполнить;
* нужно менять `.env`, домен, оплату, внешний сервис или деплой;
* обнаружен конфликт с пользовательскими изменениями в тех же строках;
* безопасный ожидаемый вариант нельзя определить из контекста.

Во всех остальных случаях выбери самое простое разумное решение и выполни задачу.
